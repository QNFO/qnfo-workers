**Note on the probe disagreement.** `integration_state` says `probe_gap` is 1 of 80 while
`fleet_status` shows 43 of 55 with `healthy: null`. These are **not** contradictory:
`integration_state` counts a worker as "probed" if a probe **row** exists in `fleet_probe_log`,
regardless of whether the probe returned a verdict. `fleet_status` counts a worker as healthy
only if a probe returned HTTP 200. **So the fleet records that it probed; it does not record
what the probes found.** That gap between *probed* and *verdict obtained* is the defect — and it
is the same class as the registry `base_url` 404 finding (agent_issues 739): a probe that cannot
fail loudly.

## Adversarial notes

- **`integration_state` is generated BY the fleet**, so using it to audit the fleet is partly
  circular. It is used here only where it **corroborates** an independently measured figure
  (ages, counts) — never as the sole basis for a claim.
- `integration_state` reports the `research` chain as **"healthy"** while flagging **122.4h stale**
  in the same object. **Its status vocabulary disagrees with its own evidence.** Do not read
  "healthy" from this table as evidence of health.
- The 80 vs 55 `fleet_size` difference is **unexplained** here. It could be workers present in
  Cloudflare but absent from the registry, or vice versa. Not separated in this pass.
- **Not done, deliberately:** the ~38 stale `scanerr:*` keys in `fleet_deploy_state` naming dead
  workers were **not deleted**. The consumer of those keys was not identified this session, and
  mutating control-plane state whose reader is unknown is not a safe "cleanup". The dead-worker
  roster is documented instead (audit §3).
