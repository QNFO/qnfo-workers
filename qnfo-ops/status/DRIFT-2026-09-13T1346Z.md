## Defect: `github_file_write` races when issued concurrently

Writes to the same repo **must be issued one at a time**. Issued two-at-a-time in a single batch,
the first commit succeeds and every subsequent one fails with:

```
GitHub 409: is at <commit the first write just produced> but expected <head captured at batch start>
```

The quoted "is at" SHA is the commit made by the *preceding write in the same batch*. This is a
shared branch-head precondition captured once per batch and never re-read, so parallel writes
invalidate each other. Observed twice, deterministically:

- batch of `probe update` + `DRIFT create` → probe committed `ae803769`; DRIFT failed
  (`is at ae803769... but expected f67a74b8...`)
- batch of `jobs.json update` + `DRIFT create` → jobs.json committed `0245fdee`; DRIFT failed
  (`is at 0245fdee... but expected 638e9b7e...`)

Issued serially, every write succeeded. Also established, by controlled test on a throwaway file:

- payload size is **not** a factor — a 1.5 KB update succeeded, and a ~6.4 KB update succeeded
- the SHA parameter **is** forwarded — a bogus SHA yields `409: ... does not match 0000...`
- the SHA must be the **blob** SHA from `github_repo_read`, not a commit SHA (a commit SHA is
  rejected with `does not match`)
- a create in the same directory failed once while issued concurrently, so the race affects the
  create path too, not just updates

**Operational rule:** one repo write per batch, or accept that all but the first will 409.

## Caveat: `raw.githubusercontent.com` lags commits by minutes

Do not use an unauthenticated `raw.githubusercontent.com` fetch to verify a commit made seconds
earlier. Immediately after `jobs.json` and `JOBS.md` returned `ok` with new commits, raw still
served the **previous** content (`observed_through 2026-09-13T13:40:48.465Z`) at HTTP 200 — a
convincing but wrong "the write did not land". The GitHub contents API showed the committed state.
Any "verified by raw fetch" claim made within minutes of a write is worthless.

## Standing defect

**D17** remains the reason the numbers above matter less than they look: 39 jobs sit in
`status='continuing'` with a finished answer already written, so a poller reads `continuing`
forever. A keyless status surface is cosmetically satisfied and functionally useless until the
terminal status is written in the same statement as `response`.
