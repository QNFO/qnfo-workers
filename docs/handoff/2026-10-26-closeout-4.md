## 3. What the review found (kept, because each is a lesson for the next filer of this kind)

- The playbook validator was bypassed in three adversarial rounds, eight ways in all: a row with `?1` anywhere passed; an `OR`, a `NOT`, a CASE in the SET list, `UPDATE ... FROM`, a cross join that fills `issue_id` from another table,
  a second `ON CONFLICT` clause keyed by `class`, a re-keying `SET`, and a NUL that SQLite treats as the end of the statement. Each now has a must-refuse case that is also run on real SQLite, and a generated-statement property test
  (12,468 + 1,060 statements) asserts that no accepted statement changes another issue's row. Against the unfixed validator the same tests fail (105 of 1,060 generated statements change another issue).
- The probe author (PROBE-AUTHOR-LIVEPATH-1) had never run: the remediation tick called `rtEnsureLivePath(db, out)` without `env`, so every call ended in `no-ai-binding`, 77 PROBE-NEEDED-1 filings produced 0 authored probes. Fixed in 0.54.0 (switch `ops_config rt_probe_author = off`).
- A closing probe that needs an owner act is unreachable once the owner's own directive removes the act (100360, section 5). A probe measures what the issue delivered.
- A closing probe that reads rows the deploy itself creates must fail closed while they are missing: the probe of issue 1000426 ran six seconds before migration 628 created `PN-R2`, fell through to `ok` and closed the issue
  with its findings open (`remediation_verifications` 324090). It was caught within minutes, the probe now refuses a missing row, the issue is reopened (`issue_lifecycle`: reopened) and `decision_log` holds the correction.
- A wall-clock budget in a test (`remediation-slot`, 5 ms) is a load-dependent flake, not a product defect: assert the invariant.
