
NO-PROGRESS-CEILING-1 (agent_issues 2726, pillar autonomy). Owner directive 2026-10-17: "no single critical path shall ever hold up any fleet function, process, or workflow."

**Defect, measured 2026-10-17:** the code loop allows one unfinished task per file (CODE-DISPATCH-DEDUPE-1, pathBusy) with no ceiling on how long that task may hold the file. ct_2qutwnt9q6xdjy held qnfo-research-exec/worker.js from 01:00Z to 09:46Z: 6 attempts while issues 2407 and 2538 were refused "path busy" on every tick, and 2724 and 2725 queued behind it.

**Redesign: the cap is on LACK OF PROGRESS, not on time held.** A task that keeps failing in *new* ways is working: each new failure signature means it fixed something and found the next defect, and cutting it would throw that work away. A task that only reprises failures it has already produced is looping. noteSig now stamps ctx.last_new_sig_at for the attempt that leaves a signature the task has not produced before, persisted with ctx.sigs and carried through the ctx rebuild. pathBusy fails the blocking task only when that stamp is older than path_hold_max_min (ops_config, default 180, floor 30) and the task has at least 2 failed attempts: it is set failed with a NO-PROGRESS-CEILING-1 reason that keeps its last error, its claim is released (outcome abandoned), one code-task.no-progress event is written, and the file is free on the same call. A task inside the window, on its first attempt, or with no recorded signature keeps the file exactly as before. VERSION 0.16.2 -> 0.17.0-no-progress; mirror identical.

**Why this is better than the time cap it replaces:** the earlier draft cut any task past 3 h with 2 failed attempts, which would also discard a slow but progressing task. Here an old task that is still finding new failures keeps the file (test 7g), and a task that stops producing new failures, including the observed alternation A B A B where the same failure comes back after a different one, is cut after the window regardless of how long it has been alive. The measure is attempt history, so backoff-spaced attempts cannot smuggle a stuck task past the ceiling: the stamp only moves when a genuinely new failure appears.

**Not in this PR:** bundling several issues on one file into one task (the second half of issue 2726). It changes intake and the merge runner's scope and needs its own PR.

**Tests:** dispatch-dedupe section 7 covers the no-progress cut, the progress exception (old task, new signatures, keeps the file), no-signature tasks, and the ops_config window. Local: 47 passed, 0 failed; fail-signature-stop, claim-backoff, claims-first, claim-at-run, timeout-retry, noop-gate and large-file all pass. The test shim now binds ?N placeholders by name, because node:sqlite on Node 22/Windows refuses positional ?N binding ("column index out of range"), which is what made sections 1-5 fail on this checkout before the change; semantics unchanged.

**Risk:** a task that keeps producing new signatures without ever succeeding is not cut by this ceiling; the existing 9-attempt exhaustion and per-task ladder still bound it, and such a task is by construction making progress rather than looping. If the 180-minute window is too tight for a slow environment, raise ops_config path_hold_max_min.
