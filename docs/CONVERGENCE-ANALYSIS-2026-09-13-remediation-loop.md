**Correcting revision 2.** I described the load as "a swarm of concurrent agents".
The data says otherwise.

**Job fan-out, 13:00Z → 14:30Z** (`ops_jobs`):

| metric | value |
|---|---|

| carrying the prompt `AUDIT AND FIX ALL FLEET ERRORS, WARNINGS, AND STALE WORKERS` | **77 (70%)** |

| carrying an `assistant` turn — i.e. **continuations, not fresh requests** | **110 of 110 (100%)** |

### What this explains

1. **My `demo-heartbeat` deletion was reverted in ~13 minutes** — a re-running
   continuation re-applied a peer's change.
2. **The `alerts` ledger was purged mid-session** (critical 717 → 4, `info` 59 → 11,
   newest id 1117 → 1076) by a continuation executing a write.
3. **Backlog 21 → 47 in one session**; **70 issues filed today**; **~193 same-day
   audit documents** — all written by continuations of the same instruction.
4. **100–400 tool calls/minute** is 110 chained jobs, not 110 agents.

**Root cause of the fleet's "numerous errors": the ops endpoint is re-executing the
same audit-and-fix instruction as 6-deep chained continuations, each carrying the full
prior conversation.** The fleet's errors are not being generated by the fleet; they
are being *re-observed and re-reported* by the loop that is supposed to fix them.

## 4. Consequence: writes are unattributable by construction

- `cloud_ops_events` for `ops_ai_tool` stores **only the tool name** in `text`. No
  SQL, arguments or target table.
- `cloud_ops_events` has no session column; `job` is `'qnfo-ops'` on every row.
- `ops_ai_log` columns: `id, ts, model, strategy, complexity, domain, prompt,
  response, prompt_tokens, completion_tokens, cost_usd, latency_ms, tool_calls,
  source, ua, streamed, ok` — **no session or instance identifier**.

With 244 writes in 9.5 minutes across 9 concurrent jobs and no actor id, **the writer
of any given row cannot be identified.** A schema gap, not a search gap. The promise
"every write is logged to cloud_ops_events" holds only as *"a write happened"*.

## 5. The apply path, precisely bounded

| route | limit | consequence |
|---|---|---|
| `github_repo_read` | 32,768 chars, no offset | cannot read `qnfo-fleet-control/worker.js` (75,875 B) or `qnfo-observability/worker.js` (37,386 B) |
| `r2_get` | **also caps ~32,768** — verified: `maxChars=40000` on a 34,825 B object returned `truncated:true` | **not** a workaround |
| `workspace_read` | 100,000 chars | only if the file was already stored there |
| writes | full body in one call | cannot round-trip a file it cannot read |
| deploy | none bound | `fleet_deploy_state` `enabled=0`, `auto_heal=0`; re-affirmed 0 at 14:26:29 |

Read-cap × write-whole × no-deploy. Two legs are hard limits of this endpoint.

## 6. What would actually converge

**First, and cheapest — stop the fan-out:**
1. **Cap or eliminate self-chaining.** 100% of jobs are continuations; chain depth is
   reported as up to 6. Each leg re-sends the full conversation, so cost scales with
   depth² in practice. A depth of 1 with explicit resumption would cut spend by an
   order of magnitude.
2. **Dedupe identical in-flight prompts.** 77 jobs carried the same instruction. A
   hash of (prompt, in-flight) collapses the fan-out to one.
3. **Stop re-submitting the same instruction.** Re-running "audit and fix fleetwide"
   produces another document and another 47 tickets; it does not apply a fix.

**Then:**
4. **One session with `wrangler`.** Six staged patches in `qnfo-fleet-control/` and
   four fixes in
   `qnfo-pipeline-ops/FINDING-2026-09-13-alert-storm-and-dedupe-are-one-bug.md` are
   written and waiting.
5. **Add an instance/session identifier** to `ops_ai_tool` events and `ops_ai_log`,
   with the write target.
6. **Extend the cost gate to the ops endpoint's provider.** $64.73 in one day is
   invisible to a gate that reads Workers AI neurons.
7. **Cap the backlog.** `qnfo-fleet-advisor` emitted this at 14:21:14Z: *"Hard-cap
   open-issue backlog at 50 items; enforce 48-hour triage or mandatory 'Won't Fix'
   closure for all overflow."* With 47 open, the cap binds immediately.

## 7. Failure modes of this analysis

- **I am inside the loop I measured.** Revision 3 is itself a continuation job
  carrying the full conversation. Its own cost is part of the $64.73. **The correct
  response to this finding is to stop generating turns, not to generate another.**
- **The tool-call counts may double-count.** Duplicate-looking `job-run` pairs exist
  (two identical `processed 30` rows 0.4 s apart at 14:24:20/21). Order of magnitude
  is robust; the precise figure is not.
- **"70% carry the same prompt" counts substring matches** on `payload LIKE '%AUDIT
  AND FIX%'`, which includes quoting of the prompt inside a longer context.
- **A genuine degradation event could also contribute** to the filing spike. I did
  not test whether 2026-09-13 saw more real failures; err24 (26) is not abnormal.
- **"Duplicated titles" is a judgement about filenames, not content** — not diffed,
  not counted.
- **The `alerts` purge is still unattributed.** Shown unattributable with the current
  schema; a non-ops writer (worker or cron) is not excluded.
