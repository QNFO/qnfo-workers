## 3. Red set — measured, not claimed

```
red_snapshots #4  12:26:55Z   (snapshot #3 at 12:20:21Z in brackets)
open_issues 222 [204]     breach_contracts 47 [48]     failed_code_tasks 90 [77]
monitored_conditions 62   retired_probes 42   parked_breaches 91
queued 36 across 15 files             red_total 312 [281]
```

**Red went UP between snapshots and that is the expected shape, not a regression.** Dispatch is
what makes failures visible: 40 tasks went into the code loop, the loop attempts them, and the
ones it cannot land turn into `failed` (77 → 90). Other loops file new issues at the same time
(204 → 222 in seven minutes). A single pass cannot outrun that; the hourly drain is the mechanism,
and `red_total` is the number to watch trend-wise, not the number for one hour.

What changed to get here:
* **788 contracts superseded** that could never be verified — 545 sat on *closed* issues, 243 pointed at *no issue at all*.
* **60 metric-condition contracts → `monitoring`** (one had been re-probed **402 times**; a probe reading `metric_registry` is a condition, not a retryable remedy).
* **91 breaches → `escalated`** where the probe had run past 5× `max_attempts` with no code task in flight.
* **55 `METRIC-TRIGGER-*` cards → `monitoring`** — they were in the defect register, which is why the count could never reach zero.
* **40 code tasks dispatched** from open issues carrying `code-task:` directives that had no task behind them.
* **`UPG-qnfo-evolve` closed and verified** — the only real `upgrade-compat` gap. Live compat moved 2026-08-01 → 2026-10-10 (PR #2046, 53/53 tests), and the fleet's own `qnfo-ops:compat-verify` runner confirmed it at 12:25:20Z.

## 4. Unresolved — carry these forward

1. **77 failed code tasks are deterministic**, not transient (transport requeue matched 0). Clusters: goal-review rejection (13), "worker suites fail after the edit" (8), 9-attempt exhaustion. Each needs a loop-quality fix, not a retry.
2. **222 open issues** are the genuine defect register. 47 have an active failing contract under work; the rest need model turns. The register grows by roughly two items a minute from the fleet's own loops, so the trend in `red_snapshots`, not any single hour, is the signal.
3. **`version-bump-guard` misreports on new branches** — PR #2012's push run said "unchanged VERSION" while VERSION moved 1.2.0→1.3.0 and live served 1.3.0. Not root-caused. The guard's base resolution looks wrong for a branch's first push.
4. **`ct_im2817` is held** with reason: the fix is a D1 migration (`AGENT-ISSUES-TRIGGER-DEPTH-1`), which the code loop cannot apply to a worker path. Needs a `migrations/*.sql` author.
5. **Repo export drifts**: `docs/fleet-tasks-canonical.json` is a dated snapshot and lags D1 (`fleet_tasks_canonical` is the drift gate's source and IS in sync). No exporter script exists — that is the missing piece if the file is to stay honest.
6. **Code-loop throughput is file-bound**: 49 queued tasks across 15 files, per-file serialization, 2-minute leases. Adding tasks faster than files free up does not increase throughput.
