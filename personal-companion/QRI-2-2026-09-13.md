# QRI-2 — gate composition defect, executed 2026-09-13

Author: qnfo-ops endpoint. Every number below is from a tool return in-session.
Supersedes the QRI-1 claim that the gate was complete. The QRI-1 work stands; this
records what it missed and what was done about it.

## 1. The finding

QRI-1 landed a composed gate (`lib/gate.js`) so that no caller could check one
violation class and publish on the other. It composed `grounding.js` + `voice.js`
and passed their violations straight to `publishPolicy`, which blocks on ANY
violation. Executing the committed modules against the real rows and the live text
showed the composition was wrong in **both directions at once**.

### Defect A — false block (the gate would withdraw a legitimate piece)

`voice.js` check 3 matches a straight-apostrophe possessive. The serial
*The Hand That Signs* (`companion_pieces.id=7`) contains:

> "Rowan's own handwriting is not the subject here."

That sentence names the reader in order to **exclude** him. `voice.js`'s own header
calls check 3 *"a review flag, not proof of impersonation"*. Check 1 fired on the
same piece for the abstract `"my attention"` — which the same header records as a
known false positive. Two flags, both documented as unreliable, were together
sufficient to withdraw correct prose.

```
companion_pieces.id=7  ->  voice: 2 violations
                             [impersonation]     "my attention"
                             [reader-as-subject] "Rowan's"
                             => publish = FALSE   (wrong)
```

### Defect B — false pass (the gate would publish the defect it exists to stop)

`addressee.js` was not composed in, so `reader-in-heading` was never checked.
Against the real rejection text of `companion_runs` id=442:

```
"# Field Notes for Rowan ..."   ->  voice: 0 violations
                                    => publish = TRUE   (wrong)
```

### Why QRI-1's tests could not catch either

The QRI-1 suite pinned `runGate` on the **defective** piece only. A gate that blocks
everything passes every test written only against a piece that deserves blocking.
Neither defect is visible from that fixture.

### Why gate.js rev 4 classifies by kind, not only by severity

Rev 3 filtered on `severity === 'warn'`, which only works once `voice.js` rev 3 is
deployed. The first write of `voice.js` rev 3 was rejected (`GitHub 409`, see §5).
A gate that silently no-ops when its detector is one revision behind is worse than
no gate: the false block would persist while the code read as if it were fixed.
Rev 4 therefore treats the two documented review flags as review flags by kind as
well as by severity. The policy lives in the composition layer — the detector
reports findings, the gate decides what blocks.

### Why `voice.js` rev 3 adds no helper function

`addressee.js` already exports `blockingViolations`, and the deploy patcher inlines
all four modules into ONE scope with exports stripped. A second top-level
declaration of that name would be a duplicate declaration and the inlined worker
would not parse. Callers filter on the `severity` field, or on `kind`.

## 5. Concurrency finding (new, operational)

Writes to `personal-companion/lib/` were rejected with `GitHub 409` three times,
each citing a **different** blob sha for the same path (`1cca0e95`, then `460481db`,
then success), while a fresh read of the same file returned the original sha
`995c80ec` both before and after. `gate.js` was rewritten by another writer between
my read and my write (3,376 → 5,530 bytes, rev 2 with the addressee fix).

Interpretation: **at least one other writer is active on `personal-companion/lib/`
concurrently with this session.** That is why `gate.js` rev 4 classifies by kind
rather than trusting a detector field, and why every write here was retried against
a freshly-read sha rather than a cached one. Anyone re-running this remediation
should expect the same races and should re-read before each write.

Not verified: whether that writer is another agent session, a fleet self-heal pass,
or a human. The evidence is the sha churn and one superseded revision, nothing more.

## 7. Adversarial note

- **The strongest argument against this work:** it lands four files and **changes
  nothing in production**. The live piece still says "Five days later". That is true,
  and it is why §4 exists. The deliverables are a verified gate, an executable
  patcher, and a regression test — not a fixed site.
- **The weakest joint:** `gate.js` rev 4's kind mapping is a hard-coded policy list.
  If `voice.js` gains a fifth check and nobody adds it to `VOICE_WARN_KINDS`, the new
  check blocks by default. That default (block) is the safe direction, but it is a
  maintenance obligation recorded in code comments, not enforced by a test.
- **Not verified:** whether production v1.1.0 already contains some of this logic.
  Its source is not in the repo, so all statements about the running gate are
  inference from `companion_runs` and published output.
- **`--fail-closed` is still not applied by default.** `COMPANION_KEY` is unset on the
  live deployment, so inverting `authorized()` would black out `reading.q08.org` on
  the next deploy. `/api/pieces` remains public with no key, returning all 7 pieces
  including `anchor_json` and `quality_json`, while the masthead reads "Private."
